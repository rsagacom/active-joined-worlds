## SDLC 六阶段总览（不可跳过，不可合并）

| 阶段 | 名称 | 核心动作 | 关键交付物 | 决策点 |
|------|------|---------|-----------|--------|
| P1 | 需求分析+设计 | 需求澄清→技术调研→PRD→架构设计→原型设计 | PRD + 架构方案 + 原型 | 5 个决策点全部确认 |
| P2 | 编码实现 | 严格按 PRD 和架构编码 | 源码 + 模块 | 每文件对应 PRD 需求 |
| P3 | 测试验证 | 单元+边界+错误路径+集成 | 测试报告 + 覆盖率 | 行≥80%/关键≥90%/分支≥70% |
| P4 | 综合审查 | 代码/测试/集成/PRD追溯 | 审查报告 + 追溯表 | 全部通过 |
| P5 | 部署交付 | commit+push+PR+文档 | PR + 交付报告 | 用户确认后合入 |

## P1 详细要求（需求分析+设计）

### 1. 需求澄清+智能补充

对用户的每个任务，从以下三个层次补充：
- **核心功能**：用户明确要求的
- **扩展功能**：常见配套（如登录→忘记密码/记住我，数据→分页/搜索/筛选）
- **相关功能**：体验提升（加载态/错误态/空态/反馈/权限）

系统性提问覆盖：功能范围、目标用户、技术约束、非功能需求、UI偏好、数据集成。

**决策点1：需求确认后写入 project-state.md，不得跳过。**

### 2. 技术调研+技术栈确认

- 后端：Rust (Gateway) + JavaScript (H5 Web Shell)
- 前端：原生 DOM API + CSS Variables，禁止引入 React/Vue/Angular
- 测试：Node.js 原生 test runner (`node --test`)、Rust `cargo test`
- UI（必须调用 ui-ux-pro-max skill）：硬朗像素风、实色边框、CSS 变量驱动

**决策点2：技术栈确认。**

### 3. PRD 编写与确认

PRD 格式（≤150 行）：
```
需求清单：ID | 描述（≤30字） | 验收标准（按优先级排序）
技术栈：已确认的技术选型
非功能需求：性能/安全/兼容性
UI方向：像素风 + 三层结构（场景图→热点层→聊天气泡）
```

**决策点3：PRD 确认后写入 .claude/prd.md。PRD 锁定，严格执行。**

发现 PRD 遗漏 → 回退 P1 与用户确认。禁止在 P2 擅自扩展。

### 4. 架构设计+方案对比

提供 2-3 个方案，每个含：
- 模块划分
- 数据模型变更
- API/端点设计
- 优缺点 + 适用场景

**决策点4：用户选择架构方案后锁定。**

关键架构约束（已有，不可违反）：
- Gateway 是唯一状态真源，H5/TUI/CLI 只消费不制造 canonical state
- pending echo 只能作为 UI 发送中状态，必须能被 committed copy 替换
- 前端不做 localStorage 缓存房间权限/身份真值
- 三层结构：底层像素图 → 中层透明热点 → 顶层聊天气泡/Composer

### 5. 原型设计（涉及 UI 时强制）

- 应用 ui-ux-pro-max 设计系统
- 现代 CSS（Flexbox/Grid），自包含 HTML
- 响应式验证（375/768/1440px）
- 硬朗像素风，反对大面积磨砂玻璃和营销式英雄页

**决策点5：设计确认，锁定设计系统。**

### 6. 推进 P2

5 个决策点全部确认 → 写入 project-state.md → 自动驱动到 P2。

## P2 详细要求（编码实现）

**自动驱动，但必须遵守以下硬性约束：**

### 编码规范（.claude/rules/02-coding-standards.md）

| 指标 | 限制 |
|------|------|
| 函数体行数 | ≤ 50 行 |
| 嵌套层级 | ≤ 3 层 |
| 函数参数 | ≤ 4 个 |
| 单一职责 | 函数名不能用 "and" 连接 |

### PRD 约束（最高优先级）

- 每写一个函数，必须能回答"对应 PRD 哪条需求？"
- **禁止添加** PRD 未列出的功能
- **禁止减少** PRD 中的需求
- **禁止"顺手"重构无关代码**
- 发现 PRD 遗漏 → 停止编码，回退 P1

### 安全规范

- SQL 注入：参数化查询
- XSS：用户输入 HTML 转义
- 硬编码密钥：禁止
- 日志泄露：不记录敏感信息

### 大文件操作规则

- app.js / styles.css 拆分前必须先备份到外盘
- 禁止用行号偏移+批量删除处理大文件
- 优先使用函数名/上下文校验
- 每抽一个模块跑一次语法检查和测试
- 如果 diff 不可审阅或测试大面积失败 → 立即停止

### 可并行派发

可将独立模块派发给 `sdlc-coder` Agent 并行编码。

## P3 详细要求（测试验证）

**自动驱动。关键规则：**

### PRD 驱动测试

1. P3 开始时先列出 PRD→测试映射表（R1→test_xxx, R2→test_yyy...）
2. 逐条覆盖，不为 PRD 外代码写测试

### 覆盖率要求

| 指标 | 目标 |
|------|------|
| 新增代码行覆盖率 | ≥ 80% |
| 关键业务逻辑覆盖率 | ≥ 90% |
| 分支覆盖率 | ≥ 70% |

### 测试执行效率规则（关键！）

1. 测试命令只运行一次，`tee /tmp/sdlc-test-output.txt` 保存输出
2. Read 读取输出文件分析所有结果
3. 如有失败 → 一次性收集所有错误 → **批量修复** → 再跑一次验证
4. **整个 P3 最多运行 3 次测试命令**
5. 禁止反复执行同一测试、禁止 `-t "name"` 单跑、禁止每修一个跑一次

### UI 测试（涉及前端时强制）

- 视觉回归：Playwright 截图对比
- 响应式：375/768/1440px 三断点
- 可访问性：axe-core 0 违规
- 交互：Testing Library 用户行为模拟

## P4 详细要求（综合审查）

**自动驱动。这是正式审查，不可敷衍。**

### 审查清单

1. **代码**：Lint/Typecheck/Build 通过，符合编码规范，无安全漏洞
2. **测试**：每条 PRD 有测试且通过，覆盖率达标
3. **集成**：PRD 追溯无断链、无 PRD 外变更、全局一致
4. **UI**（如有）：设计一致、响应式三断点、可访问性通过

### 必须输出

- 审查报告：发现的问题、严重程度、修复建议
- PRD 追溯表：需求ID → 架构决策 → 代码位置 → 测试位置

### 审查不通过处理

- 轻微问题 → 修复 → 重新审查
- 严重问题（安全/架构偏离/PRD 断链）→ 回退到对应阶段

## 架构约束（来自全局记忆，不可违反）

1. **Gateway 是唯一合同真源** — H5/TUI/CLI 只消费不制造 canonical state
2. **H5 是当前主入口** — TUI 是并行客户端，不拉回 TUI-first
3. **三层 UI 结构** — 底层像素图、中层透明热点、顶层聊天气泡/Composer
4. **前端三层不缓存权威权限** — 房间权限、身份、消息真值由 Gateway 提供
5. **左边栏 = 导航栏 + 会话栏 + 用户栏** — 可滚动、可搜索、头像=个人房间入口
6. **个人房间双层配置** — image_layer + hotspot_layer，由 Gateway 保存下发
7. **admin-ds 是正式后台方向** — 不再另起新后台设计

## 禁止事项（来自全局记忆）

1. 不要重做项目
2. 不要把像素 IM 改成游戏 UI
3. 不要用大面积半透明玻璃面板遮住场景
4. 不要在 H5 端用 localStorage 缓存应由 Gateway 决定的权威状态
5. 不要把 admin-ds 样式套到所有旧页面
6. 不要删除大文件、模型、外盘资料或 Git 历史
7. **不要提交 git，除非用户明确要求**
8. 不要把大包、导出包、临时包写入 Mac 内盘
9. 不要重构与当前 PRD 无关的代码

## 用户偏好（来自全局记忆）

- 默认用中文回复
- 直接、具体、可执行，不要空泛安慰
- 先读仓库和文档，再下判断
- 大改前备份，改后测试验证
- 宣布"完成"前必须有可复现验证
